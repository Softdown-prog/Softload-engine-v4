snapshot vs manifesto — os dois níveis de dado que uma sessão do Workspace guarda

Toda sessão do Workspace (Firestore:
clientes_premium/{email}/projetos/{pid}/sessoes/{sid}) tem um campo
"snapshot" que representa o estado atual do template daquela sessão. Esse
campo aparece em dois "tamanhos" diferentes, e confundir os dois já causou
pelo menos um bug real de produção (ver o arquivo sobre manifesto
ausente nesta mesma pasta).

Snapshot RESUMIDO — campos: compilacaoId, siteName, colorPreset,
typography, gridLayout, nichoTema, xmlPath, gcPath, snapshotEm. É o
suficiente pra mostrar um card na lista de projetos (nome, cor,
tipografia) e pra baixar o XML direto (via xmlPath/gcPath). É criado
quando uma sessão nasce vinculada a uma compilação já existente — seja
pegando a última compilação global do usuário (POST
/api/workspace/projetos/:pid/sessoes) seja importando uma compilação
específica escolhida (POST /api/workspace/importar).

Snapshot COMPLETO — tudo do resumido MAIS o campo manifesto: o objeto
inteiro de configuração usado pra recompilar o template (siteName,
nichoTema, colorPreset, buttonStyle, typography, gridLayout, footerStyle,
designVoice, sidebarPosition, heroTitle, heroSubtitle, enableSeo,
lazyLoad, categoryBadges, modules{...}, e opcionalmente customCss,
svgLogo, heroHtml, staticSections, darkTheme). É criado por
_snapshotDeManifesto() (chat/chatTemplateCompiler.js), chamado depois de
QUALQUER compilação feita via chat — geração nova ou edição aplicada.

Por que a distinção importa: o chat do Workspace só consegue entrar em
modo de edição agêntica quando tem o manifesto completo — sem ele, não há
como saber os valores atuais dos campos pra montar uma edição incremental.
Um snapshot resumido sozinho não é suficiente, mesmo tendo o siteName e a
cor certos.

Onde o manifesto completo já é sempre gravado corretamente: sempre que uma
compilação passa pelo pipeline via chat (finalizarCompilacao, em
compilerPipeline.js, grava o manifesto completo no doc de `compilacoes` —
essa parte nunca teve o bug). O que faltava era COPIAR esse manifesto de
volta pro snapshot da sessão nos dois pontos de criação que citei acima —
já corrigido, e também existe um backfill automático em runtime
(workspaceChat.js) pra sessões antigas que ainda não tiverem o manifesto
salvo: se o snapshot tem compilacaoId mas não tem manifesto, o backfill
busca no doc de compilações e persiste de volta na sessão.

Regra prática: qualquer código novo que crie ou atualize um snapshot de
sessão do Workspace deveria, por padrão, incluir manifesto sempre que
estiver disponível na mesma operação — nunca assumir que o snapshot
resumido é suficiente pra qualquer consumidor futuro.
